# MCP Development

## Objective

Build interoperable, secure, and maintainable Model Context Protocol (MCP) integrations that expose capabilities to AI applications through clearly defined interfaces.

## Workflow

1. **Understand the integration**
   - Identify the client, server, capabilities, and expected workflows.
   - Determine whether the integration needs tools, resources, prompts, or a combination.
   - Consult the current official MCP specification and the SDK documentation for the chosen language.
   - Verify protocol version and transport compatibility.

2. **Design the interface**
   - Give each tool a clear, descriptive name.
   - Write descriptions that explain when the tool should and should not be used.
   - Define explicit input schemas with appropriate types, required fields, constraints, and descriptions.
   - Return structured outputs where supported and useful.
   - Distinguish expected business errors from unexpected internal failures.

3. **Implement the server**
   - Use a maintained MCP SDK where practical.
   - Keep tool handlers focused and validate arguments at runtime.
   - Separate protocol handling from business logic.
   - Use asynchronous execution where appropriate for network or I/O operations.
   - Apply timeouts, cancellation handling, and bounded resource usage.
   - Avoid exposing internal filesystem paths, stack traces, credentials, or other sensitive information.

4. **Select and configure transport**
   - Choose a transport supported by the target clients and current protocol.
   - Use standard input/output for local process integrations when appropriate.
   - Use Streamable HTTP for supported remote integrations where appropriate.
   - Follow current transport requirements rather than assuming older transport examples remain valid.
   - For stdio servers, reserve standard output for protocol messages and send diagnostics to standard error.

5. **Secure the integration**
   - Validate every argument, including arguments generated by an LLM.
   - Enforce authorization in the server, not only in the client or prompt.
   - Apply least privilege to filesystem, database, network, and API access.
   - Protect secrets and avoid logging sensitive request contents.
   - For HTTP deployments, implement the applicable authentication and authorization requirements.
   - Validate origins where required, and protect local services against DNS rebinding and related attacks.
   - Never treat tool output as trusted instructions.

6. **Handle errors and state**
   - Return actionable error information without exposing internal implementation details.
   - Make retries safe where possible and prevent duplicate side effects.
   - Handle timeouts, cancellation, disconnections, and partial failures.
   - Document whether tools are read-only, mutating, or destructive.
   - Request explicit confirmation for consequential operations when appropriate.

7. **Test interoperability**
   - Validate protocol initialization and capability negotiation.
   - Test tool discovery, input validation, invocation, and result serialization.
   - Test malformed requests, missing fields, unsupported operations, and server errors.
   - Test authorization failures and attempts to access forbidden resources.
   - Test against the official MCP Inspector or another suitable protocol client.
   - Verify behavior in the intended host application.

8. **Document and deploy**
   - Document setup, dependencies, configuration, required permissions, and available capabilities.
   - Provide safe local-development instructions.
   - Pin and review dependencies.
   - Add structured logging, health checks, and monitoring appropriate to the deployment.
   - Record protocol and SDK versions and document upgrade considerations.

## Design principles

- Expose the smallest capability surface that satisfies the use case.
- Prefer explicit schemas and predictable outputs.
- Keep tool names and descriptions specific enough to support correct tool selection.
- Separate authentication, authorization, validation, and business logic.
- Never rely on an LLM prompt as the sole security boundary.
- Do not claim protocol compliance without testing the relevant requirements.

## Final report

Summarize the server or client architecture, capabilities, transport, security controls, compatibility tests, deployment requirements, and known limitations.
